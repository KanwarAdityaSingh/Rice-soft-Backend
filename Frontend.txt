4.2 CREATE USER 
================================================================================

API ENDPOINT:
POST http://localhost:3000/api/v1/users/createUser

HEADERS:
Authorization: Bearer {token}
Content-Type: application/json

REQUEST BODY:
{
  "username": "john_sales",
  "email": "john@example.com",
  "password": "password123",
  "full_name": "John Salesman",
  "phone": "9876543210",
  "user_type": "salesman"
}

REQUIRED FIELDS:
- username (string, unique)
- email (string, valid email, unique)
- password (string, min 6 characters)
- full_name (string)
- user_type (enum: admin, salesman, vendor, broker, custom)

OPTIONAL FIELDS:
- phone (string)

SUCCESS RESPONSE (201):
{
  "success": true,
  "message": "User created successfully",
  "data": {
    "id": "uuid",
    "username": "john_sales",
    "email": "john@example.com",
    "full_name": "John Salesman",
    "phone": "9876543210",
    "user_type": "salesman",
    "is_active": true,
    "last_login": null,
    "created_at": "2025-10-27T10:49:03.240Z",
    "updated_at": "2025-10-27T10:49:03.240Z"
  },
  "timestamp": "2025-10-27T10:49:03.249Z"
}

ERROR RESPONSES:
- 409: Username or email already exists
- 400: Validation error (e.g., password too short, invalid email)
- 401: Unauthorized (invalid or missing token)

FORM VALIDATION:
Client-side validation before API call:
- Username: required, alphanumeric
- Email: required, valid email format
- Password: required, minimum 6 characters
- Full Name: required
- User Type: required, must be valid enum value
- Phone: optional, if provided validate format

IMPLEMENTATION:
1. Show create user form (modal or separate page)
2. On submit, validate client-side
3. Call API with form data
4. On success: Show success message, close form, refresh users list
5. On error: Display error message from API response

IMPORTANT - VENDOR/SALESMAN/BROKER USERS:
When creating users with user_type = "vendor", "salesman", or "broker", you need to collect
additional entity-specific information. You have two implementation options:

OPTION 1: Two-Step Process (Recommended for better UX)
1. Create user via /api/v1/users/createUser
2. After successful user creation, collect entity-specific details:
   
   - For VENDOR users:
     Use POST /api/v1/vendors/create with vendor details (business_name, address,
     business_details, bank_details, vendor type, etc.)
   
   - For SALESMAN users:
     Use POST /api/v1/salesmen/create with salesman details (name, phone, email)
     Note: Salesman creation is simple, only needs name/phone/email
   
   - For BROKER users:
     Use POST /api/v1/brokers/create with broker details (business_name, address,
     business_details, broker_details, broker type, etc.)

OPTION 2: Direct Entity Creation (One-Step Process)
Instead of creating user first, use the dedicated entity endpoints directly:
- POST /api/v1/vendors/create
- POST /api/v1/salesmen/create  
- POST /api/v1/brokers/create

These endpoints automatically create BOTH the user record AND entity-specific data in one call.

RECOMMENDATION:
- For Admin users: Use /users/createUser (simple, no additional data needed)
- For Vendor/Broker users: Use Option 2 (direct entity endpoints) for cleaner workflow
- For Salesman users: Either approach works (salesman data is minimal)

// api/vendors.js
export const vendorsAPI = {
  getAll: (includeInactive, type) => {
    let url = `${API_BASE_URL}/vendors/getAllVendors`;
    const params = new URLSearchParams();
    if (includeInactive) params.append('include_inactive', 'true');
    if (type) params.append('type', type);
    if (params.toString()) url += `?${params.toString()}`;
    return axios.get(url);
  },
  
  getById: (id) => 
    axios.get(`${API_BASE_URL}/vendors/getVendorById/${id}`),
  
  create: (data) => 
    axios.post(`${API_BASE_URL}/vendors/createVendor`, data),
  
  update: (id, data) => 
    axios.post(`${API_BASE_URL}/vendors/updateVendor/${id}`, data),
  
  delete: (id) => 
    axios.post(`${API_BASE_URL}/vendors/deleteVendor/${id}`),
  
  lookupGST: (gstNumber) => 
    axios.get(`${API_BASE_URL}/vendors/lookupGST?gst_number=${gstNumber}`),
  
  lookupPAN: (panNumber) => 
    axios.get(`${API_BASE_URL}/vendors/lookupPAN?pan_number=${panNumber}`),
  
  quickCreateFromGST: (data) => 
    axios.post(`${API_BASE_URL}/vendors/quickCreateFromGST`, data),
  
  quickCreateFromPAN: (data) => 
    axios.post(`${API_BASE_URL}/vendors/quickCreateFromPAN`, data)
};

9.3 GST LOOKUP FLOW
================================================================================

async function handleGSTLookup(gstNumber) {
  try {
    setLoading(true);
    const response = await vendorsAPI.lookupGST(gstNumber);
    const mappedData = response.data.data.mapped_data;
    
    // Auto-fill form fields
    setFormData(prev => ({
      ...prev,
      business_name: mappedData.business_name,
      address: mappedData.address,
      business_details: {
        ...prev.business_details,
        gst_number: gstNumber,
        ...mappedData.business_details
      }
    }));
    
    showSuccess('GST details fetched successfully');
  } catch (error) {
    showError('Failed to fetch GST details');
  } finally {
    setLoading(false);
  }
}


9.4 FORM VALIDATION PATTERNS
================================================================================

// GST Validation
const validateGST = (gst) => {
  const gstRegex = /^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z]{1}[1-9A-Z]{1}Z[0-9A-Z]{1}$/;
  return gstRegex.test(gst);
};

// PAN Validation
const validatePAN = (pan) => {
  const panRegex = /^[A-Z]{5}[0-9]{4}[A-Z]{1}$/;
  return panRegex.test(pan);
};

// Email Validation
const validateEmail = (email) => {
  const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  return emailRegex.test(email);
};

SECTION 5: ERROR HANDLING & AUTHENTICATION
================================================================================

TOKEN EXPIRATION:
JWT tokens expire in 24 hours. Implement:

1. Token validation on app load:
   - Check if token exists in localStorage
   - If no token → redirect to /login
   - If token exists → verify it's still valid (optional)

2. Token refresh logic:
   - On 401 error, redirect to /login
   - Clear localStorage
   - Show "Session expired" message

3. Auto logout on token expiry:
   - Check token expiration before making API calls
   - Or handle 401 errors globally

API ERROR HANDLING:

Standard Error Response Format:
{
  "success": false,
  "error": "Error message",
  "message": "Optional detailed message",
  "timestamp": "..."
}

Error Status Codes:
- 400: Bad Request (validation errors)
- 401: Unauthorized (invalid/missing token)
- 403: Forbidden (insufficient permissions)
- 404: Not Found (resource doesn't exist)
- 409: Conflict (duplicate username/email)
- 500: Internal Server Error

Handle errors by showing user-friendly messages:
- 401 → "Session expired. Please login again." → Redirect to /login

===========================================
VEHICLE ENTITY WITH SUREPASS INTEGRATION
FRONTEND IMPLEMENTATION GUIDE
===========================================

## OVERVIEW

The backend has been updated to introduce a new "Vehicle" entity that replaces the simple `vehicle_number` string field in Inward Slip Passes (ISP) with a full-fledged vehicle management system. This includes:

1. **New Vehicle Entity**: Stores comprehensive vehicle information including RC details, owner information, insurance/fitness validity, and challan details
2. **Surepass RC Verification**: Integration with Surepass API to verify vehicle registration numbers and auto-populate vehicle details
3. **Auto-Sync with Transporters**: Vehicles can be linked to multiple transporters, with automatic bidirectional synchronization
4. **Updated ISP Flow**: ISPs now reference vehicles by ID instead of storing vehicle numbers directly

---

## KEY CHANGES

### 1. Vehicle Entity Structure

```typescript
interface Vehicle {
  id: string;                        // UUID
  vehicle_number: string;            // e.g., "DL01AB1234"
  rc_number: string | null;          // RC number if different
  owner_name: string | null;
  vehicle_class: string | null;      // LMV, HMV, etc.
  fuel_type: string | null;          // Diesel, Petrol, CNG, Electric
  maker_model: string | null;        // TATA ACE, MAHINDRA BOLERO
  registration_date: string | null;  // ISO date
  insurance_validity: string | null; // ISO date
  fitness_validity: string | null;   // ISO date
  permit_validity: string | null;    // ISO date
  challan_details: any[] | null;     // Array of traffic violations
  transporter_ids: string[];         // Array of transporter UUIDs
  is_verified: boolean;              // True if verified via Surepass
  verified_at: string | null;        // ISO timestamp
  is_active: boolean;
  created_at: string;
  updated_at: string;
}
```

### 2. Inward Slip Pass Changes

**BEFORE:**
```typescript
interface InwardSlipPass {
  vehicle_number: string;  // Simple string field
  // ... other fields
}
```

**AFTER:**
```typescript
interface InwardSlipPass {
  vehicle_id: string;  // UUID reference to vehicles table (REQUIRED)
  // ... other fields
}
```

**IMPORTANT CHANGES**:
- `vehicle_number` field has been **completely removed** from ISP
- `vehicle_id` is now **REQUIRED** (not nullable) when creating ISPs
- You must provide `vehicle_id` (UUID) instead of `vehicle_number` (string)
- The vehicle must exist before creating an ISP

### 3. Transporter Changes

**BEFORE:**
```typescript
interface Transporter {
  vehicle_numbers: string[];  // Array of vehicle number strings
  // ... other fields
}
```

**AFTER:**
```typescript
interface Transporter {
  vehicle_numbers: string[];  // Deprecated but kept for backward compatibility
  vehicle_ids: string[];      // NEW: Array of vehicle UUIDs
  // ... other fields
}
```

## NEW API ENDPOINTS

### Vehicle Verification (Surepass)

**Endpoint**: `POST /api/v1/vehicles/verify`

**Description**: Verifies a vehicle registration number via Surepass API and returns vehicle details. Does NOT create a vehicle record.

**Request**:
```json
{
  "vehicle_number": "DL01AB1234"
}
```

**Response**:
```json
{
  "success": true,
  "data": {
    "vehicle_number": "DL01AB1234",
    "rc_number": "DL01AB1234",
    "owner_name": "JOHN DOE",
    "vehicle_class": "LMV",
    "fuel_type": "Diesel",
    "maker_model": "TATA ACE",
    "registration_date": "2020-05-15",
    "insurance_validity": "2025-05-14",
    "fitness_validity": "2030-05-14",
    "permit_validity": "2025-12-31",
    "challan_details": []
  },
  "message": "Vehicle verified successfully"
}
```

**Error Responses**:
- `400 Bad Request`: Invalid vehicle number or verification failed
- `500 Internal Server Error`: Surepass API error

### Vehicle CRUD Operations

#### 1. Get All Vehicles

**Endpoint**: `GET /api/v1/vehicles`

**Query Parameters**:
- `transporter_id` (optional): Filter by transporter UUID
- `is_active` (optional): Filter by active status (true/false)

**Response**:
```json
{
  "success": true,
  "data": [
    {
      "id": "uuid-here",
      "vehicle_number": "DL01AB1234",
      "rc_number": "DL01AB1234",
      "owner_name": "JOHN DOE",
      "vehicle_class": "LMV",
      "fuel_type": "Diesel",
      "maker_model": "TATA ACE",
      "registration_date": "2020-05-15",
      "insurance_validity": "2025-05-14",
      "fitness_validity": "2030-05-14",
      "permit_validity": "2025-12-31",
      "challan_details": [],
      "transporter_ids": ["transporter-uuid-1", "transporter-uuid-2"],
      "is_verified": true,
      "verified_at": "2024-12-24T10:30:00.000Z",
      "is_active": true,
      "created_at": "2024-12-24T10:30:00.000Z",
      "updated_at": "2024-12-24T10:30:00.000Z"
    }
  ]
}
```

#### 2. Get Vehicle by ID

**Endpoint**: `GET /api/v1/vehicles/:id`

**Response**: Same as individual vehicle object above

#### 3. Get Vehicle by Vehicle Number

**Endpoint**: `GET /api/v1/vehicles/byNumber/:vehicleNumber`

**Example**: `GET /api/v1/vehicles/byNumber/DL01AB1234`

**Response**: Same as individual vehicle object above

#### 4. Create Vehicle

**Endpoint**: `POST /api/v1/vehicles`

**Request**:
```json
{
  "vehicle_number": "DL01AB1234",
  "rc_number": "DL01AB1234",
  "owner_name": "JOHN DOE",
  "vehicle_class": "LMV",
  "fuel_type": "Diesel",
  "maker_model": "TATA ACE",
  "registration_date": "2020-05-15",
  "insurance_validity": "2025-05-14",
  "fitness_validity": "2030-05-14",
  "permit_validity": "2025-12-31",
  "challan_details": [],
  "transporter_ids": ["transporter-uuid-1"],
  "is_verified": true,
  "verified_at": "2024-12-24T10:30:00.000Z",
  "is_active": true
}
```

**Response**: Same as individual vehicle object above

**Validation**:
- `vehicle_number` is required and must be unique
- `transporter_ids` must contain valid transporter UUIDs

#### 5. Update Vehicle

**Endpoint**: `PUT /api/v1/vehicles/:id`

**Request**: Same as create, but all fields are optional

**Response**: Updated vehicle object

#### 6. Delete Vehicle (Soft Delete)

**Endpoint**: `DELETE /api/v1/vehicles/:id`

**Response**:
```json
{
  "success": true,
  "message": "Vehicle deleted successfully"
}
```

**Note**: Vehicles linked to ISPs cannot be deleted. The API will return an error.

## UPDATED ISP FLOW

### Creating an Inward Slip Pass

**OLD WAY** (No longer works):
```json
{
  "vehicle_number": "DL01AB1234",
  // ... other fields
}
```

**NEW WAY**:
```json
{
  "vehicle_id": "vehicle-uuid-here",
  "slip_number": "ISP-001",
  "date": "2024-12-24",
  "party_name": "ABC Traders",
  // ... other fields
  // NOTE: Do NOT send "id" - it's auto-generated by the database
}
```

**Important Notes**:
- ✅ ISP `id` is **auto-generated** by the database (UUID) - do NOT send it from frontend
- ✅ The `vehicle_id` must reference an existing vehicle
- ✅ If the vehicle doesn't exist, create it first using the vehicle creation endpoint
- ✅ The response will include the auto-generated `id`

### ISP Response Format

The ISP response now includes only `vehicle_id`:

```json
{
  "id": "isp-uuid",
  "vehicle_id": "vehicle-uuid-here",
  // ... other fields
}
```

**Note**: To display the vehicle number in the UI, you'll need to fetch the vehicle details using the `vehicle_id`.

## RECOMMENDED FRONTEND WORKFLOW

### Scenario 1: Creating ISP with New Vehicle

1. **User enters vehicle number** in ISP creation form
2. **Check if vehicle exists**:
   ```
   GET /api/v1/vehicles/byNumber/DL01AB1234
   ```
3. **If vehicle doesn't exist**:
   a. **Verify vehicle** (optional but recommended):

      ```

   e. **Store returned vehicle ID**
4. **Create ISP** with `vehicle_id`:
   ```
   POST /api/v1/inward-slip-passes
   { "vehicle_id": "vehicle-uuid", ...other fields... }
   ```

### Scenario 2: Creating ISP with Existing Vehicle

1. **User selects vehicle** from dropdown/autocomplete
2. **Create ISP** directly with selected `vehicle_id`

### Scenario 3: Vehicle Management Page

1. **List all vehicles**:
   ```
   GET /api/v1/vehicles?is_active=true
   ```
2. **Allow filtering by transporter**:
   ```
   GET /api/v1/vehicles?transporter_id=transporter-uuid

3. **Verify and add new vehicle**:
   - Verify → Review → Create
4. **Edit vehicle details**:
   ```
   PUT /api/v1/vehicles/:id
   ```
5. **View vehicle history** (which ISPs used this vehicle)

## AUTO-SYNC BEHAVIOR

### Vehicle ↔ Transporter Synchronization

The backend automatically keeps `vehicle.transporter_ids` and `transporter.vehicle_ids` in sync using database triggers.

**Example**:
1. Create vehicle with `transporter_ids: ["t1", "t2"]`
2. Backend automatically adds this vehicle's ID to `t1.vehicle_ids` and `t2.vehicle_ids`
3. If you update vehicle to `transporter_ids: ["t1", "t3"]`:
   - Vehicle is removed from `t2.vehicle_ids`
   - Vehicle is added to `t3.vehicle_ids`

**Frontend Implication**: You don't need to manually update transporters when linking vehicles. Just update the vehicle's `transporter_ids` array.

## MIGRATION NOTES

### Existing Data

The migration automatically:
1. Creates vehicle records from unique `vehicle_number` values in existing ISPs
2. Links these vehicles to ISPs via `vehicle_id`
3. Links vehicles to transporters based on ISP relationships
4. Removes the old `vehicle_number` field from ISPs (no longer needed)

### Backward Compatibility

- Transporter responses still include `vehicle_numbers` array (deprecated but kept for now)
- Frontend should use `vehicle_ids` for transporters going forward
- **Breaking Change**: ISP no longer returns `vehicle_number` - you must fetch vehicle details separately

## VALIDATION RULES

### Vehicle Number Format
- Uppercase letters and numbers
- No strict format validation (varies by region)
- Automatically converted to uppercase by backend

### Vehicle Creation
- `vehicle_number` must be unique
- Cannot create vehicle with duplicate `vehicle_number`

### ISP Creation
- `vehicle_id` is **REQUIRED** (not optional)
- `vehicle_id` must reference an existing vehicle
- Backend validates vehicle existence before creating ISP
- You cannot create an ISP without first creating or selecting a vehicle

### Vehicle Deletion
- Cannot delete vehicle if linked to any ISPs
- Use soft delete (set `is_active = false`) instead

### 3. Vehicle Management Page

Features:
- List view with filters (transporter, active status)
- Search by vehicle number
- "Verify & Add New Vehicle" button

### 4. ISP Form Updates

- Replace vehicle number text input with vehicle selector
- Show vehicle details (owner, class, etc.) when selected
- "Add New Vehicle" button to open vehicle creation flow
- Validate that vehicle_id is provided before submission (REQUIRED field)

### 5. ISP List/Detail View Updates

Since ISP responses no longer include `vehicle_number`, you need to:

**Option 1: Fetch vehicles separately and join in frontend**
```javascript
// Fetch ISPs
const isps = await fetch('/api/v1/inward-slip-passes');

// Fetch all vehicles
const vehicles = await fetch('/api/v1/vehicles');

// Create a vehicle lookup map
const vehicleMap = {};
vehicles.data.forEach(v => vehicleMap[v.id] = v);

// Join in frontend
const ispsWithVehicles = isps.data.map(isp => ({
  ...isp,
  vehicle: vehicleMap[isp.vehicle_id]
}));
```

**Option 2: Fetch vehicle details on-demand**
```javascript
// When displaying ISP details
const vehicle = await fetch(`/api/v1/vehicles/${isp.vehicle_id}`);
```

**Option 3: Backend modification (recommended for performance)**
Consider requesting a backend endpoint that returns ISPs with vehicle details joined:
```
GET /api/v1/inward-slip-passes?include=vehicle
```
This would require backend changes to join vehicle data in the ISP response.

## ERROR HANDLING

### Common Errors

1. **Vehicle Not Found (404)**
   ```json
   {
     "success": false,
     "error": "Vehicle not found"
   }
   ```
   **Action**: Prompt user to create vehicle first

2. **Vehicle Number Already Exists (409)**
   ```json
   {
     "success": false,
     "error": "Vehicle number already exists"
   }
   ```
   **Action**: Suggest using existing vehicle or checking for typos

3. **Surepass Verification Failed (400)**
   ```json
   {
     "success": false,
     "error": "Vehicle verification failed: Invalid vehicle number"
   }
   ```
   **Action**: Allow manual entry or double-check vehicle number

4. **Cannot Delete Vehicle (400)**
   ```json
   {
     "success": false,
     "error": "Cannot delete vehicle that is linked to inward slip passes"
   }
   ```
   **Action**: Suggest soft delete (set is_active = false)

## EXAMPLE API CALL SEQUENCES

### Complete Flow: Verify → Create Vehicle → Create ISP

```javascript
// Step 1: Verify vehicle
const verifyResponse = await fetch('/api/v1/vehicles/verify', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${token}` },
  body: JSON.stringify({ vehicle_number: 'DL01AB1234' })
});
const verifiedData = await verifyResponse.json();

// Step 2: Create vehicle with verified data
const createVehicleResponse = await fetch('/api/v1/vehicles', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${token}` },
  body: JSON.stringify({
    ...verifiedData.data,
    transporter_ids: ['transporter-uuid-here']
  })
});
const vehicle = await createVehicleResponse.json();

// Step 3: Create ISP with vehicle_id
const createISPResponse = await fetch('/api/v1/inward-slip-passes', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${token}` },
  body: JSON.stringify({
    vehicle_id: vehicle.data.id,
    slip_number: 'ISP-001',
    date: '2024-12-24',
    party_name: 'ABC Traders',
    transporter_id: 'transporter-uuid-here',
    // ... other ISP fields
  })
});
```
